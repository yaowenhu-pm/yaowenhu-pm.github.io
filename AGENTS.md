# Repository Guidelines

## Project Structure & Module Organization

This repository is a framework-free GitHub Pages personal site. Keep each responsibility in its existing file:

- `index.html` contains document metadata, the application mount point, and module entry. The markup inside `#app` (between the `prerender:start/end` comments) is generated by `build.js` — never edit it by hand.
- `build.js` generates three independent pages: `index.html` (original introduction, photo/contact, education, then internship experience), `work/index.html` (projects and elsewhere), and `thoughts/index.html` (Thoughts only). Preserve the original introduction and education on the experience page. The root document is the shared HTML skeleton; never hand-edit generated app blocks or the two subpage files. Rerun `node build.js` after source changes.
- `js/pages.js` shares page composition between the build and `js/main.js`; `js/data.js` is the static content entry point; `js/components/` contains section renderers. Automatically curated Thoughts live in `js/thoughts-data.js` and are re-exported from `js/data.js`, so the profile editor cannot overwrite synchronized notes. Thoughts-only updates change that module and `thoughts/index.html`, not the other pages.
- Navigation uses real paths `/`, `/work/`, `/thoughts/`. Keep root-relative asset paths and preserve old section/note links through the explicit redirect rules in `js/pages.js`.
- `styles/` separates tokens, base rules, layout, components, and responsive rules. `styles/main.css` declares their order; `build.js` emits versioned links to each leaf stylesheet and an import map for JS dependencies. Ordinary Thoughts page startup binds interactions to prerendered HTML without replacing it; profile pages retain rendering for the web editor's data-only updates. Asset versions must remain unchanged for Thoughts-only data updates to preserve the publishing boundary.
- Put local images and other media in `assets/`; use lowercase, hyphenated names such as `hero-photo.jpg`.

There is no package manager or dependency install. The only build step is the zero-dependency `node build.js` prerender — do not add anything beyond it.

## Local Development & Checks

Run the site locally from the repository root:

```bash
python3 -m http.server 4173
```

Open `http://localhost:4173` and test both desktop and a 375px-wide mobile viewport. Before committing, run:

```bash
node build.js          # regenerate prerendered markup in index.html
find js -name '*.js' -print0 | xargs -0 -n1 node --check  # JavaScript syntax
git diff --check       # whitespace and patch errors
```

Run `node --test tests/thoughts.test.mjs` with Node's built-in test runner. Manually verify all three direct URLs and reloads, navigation and active states, legacy redirects, external links, rendered card counts, responsive layout, and a clean browser console. Include screenshots for visual changes in pull requests.

## Coding Style & Naming

Use two-space indentation in HTML and JavaScript, semicolons in JavaScript, and the existing CSS custom properties instead of hard-coded repeated values. Use `camelCase` for JavaScript variables and functions, plural names for collections, and descriptive kebab-case CSS classes. Keep static display content in `js/data.js`; avoid duplicating repeated cards in HTML.

## Commits & Pull Requests

Use short, imperative, capitalized commit subjects, following the existing history: `Create personal homepage` or `Update hero photo`. Keep each commit focused on one visible change.

Pull requests should state the user-facing change, list the checks run, link any relevant issue, and include desktop and mobile screenshots for layout work. Do not publish secrets, personal contact details, contract values, customer business data, or internal platform names.
